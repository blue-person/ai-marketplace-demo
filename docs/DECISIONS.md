# Decisions

This file explains why the code is the way it is. It is a log, so new decisions go at the end and old ones are not edited.

* Add a decision when a choice was made between options and someone could ask later why. A bug fix is not a decision.
* Write a short title with the date and one paragraph that says what was decided and why. Add what was rejected, the source with its link and where the code is, but only when it applies and inside the same paragraph.
* End with a sentence that starts with "Pending" when something is missing or was not verified. Without it, the decision is understood as closed.
* When a decision changes, add a new one that says "Replaces" and the old title, and leave the old one as it is.
* Asking the assistant to "register this decision" is enough, because it can write the paragraph from the work just done.

## Parameterized SQL queries (2026-11-23)

Every query sends the values of the user through `%s` placeholders, and no query joins strings with request data. OWASP lists parameterized queries as its first defense against SQL injection, and the default cursor of `mysql-connector-python` 26.10.0 separates the values from the statement, which was checked in the installed source. Escaping by hand was rejected because it is easy to miss a case, the prepared cursor was not needed, and stored procedures would add objects to maintain. Sources are the [SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html), the [Query Parameterization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Query_Parameterization_Cheat_Sheet.html) and [cursor.execute()](https://dev.mysql.com/doc/connector-python/en/connector-python-api-mysqlcursor-execute.html). It is applied in the login and the directory. After the change, the requests that used to alter the queries stopped working. Pending, the exact quotes of the OWASP pages still have to be copied before the final reports.

## Argon2id for passwords (2026-11-23)

Passwords are stored with Argon2id using 19 MiB, 2 iterations and a parallelism of 1 through `argon2-cffi`, in `backend/app/passwords.py`. OWASP puts Argon2id first and this is its minimum setting. One hash took about 36 ms in the backend container and a check took between 33 and 40 ms, far below the one second that OWASP suggests as a limit. Rejected were scrypt (the salt and the format would be handled by hand), bcrypt (OWASP keeps it for legacy systems and it cuts the password at 72 bytes), PBKDF2 (only needed for FIPS) and keeping the unsalted MD5 of the template. A pepper was considered and postponed because OWASP calls it optional, asks to keep it in a secrets vault and warns that changing it forces all users to reset the password. Source is the [Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Pending, the way to store API keys, which are random values and not chosen passwords.

## The same answer for every failed login (2026-11-23)

A wrong password, an unknown email and an account that is not active all get the same 401 and the same message, and a good login returns only the id, the name, the email and the role. When the email does not exist, the password is checked against a dummy hash so the time is similar. The OWASP Authentication Cheat Sheet asks for a generic message and lists "account disabled" among the messages to avoid. Eight requests of each kind took 0.093 s, 0.086 s and 0.088 s on average. Keeping the 403 for inactive accounts was rejected because it tells an attacker that the password is right. Source is the [Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). Pending, the limit of failed attempts, the sign up that still reveals which emails exist, and a statistical test of the timing.

## Passwords of at least 15 characters (2026-11-23)

The sign up requires 15 characters and adds no composition rules. The OWASP Authentication Cheat Sheet says that passwords under 15 characters are weak without a second factor, which this application does not have, and it advises against composition rules. The constant is `MIN_PASSWORD_LENGTH` in `passwords.py`. Pending, a maximum length of at least 64 and a block of common or leaked passwords, which OWASP also recommends.

## Every write under ACID (2026-11-23)

Each operation that writes data runs in one transaction with a commit or a rollback. The check and the change happen together, with a conditional `UPDATE` such as `WHERE balance >= amount` or with `SELECT ... FOR UPDATE`, and a plain read followed by a separate write is not used. The database also enforces the rules with unique keys, foreign keys and `CHECK` constraints. Emails are sent after the commit and no external call runs inside an open transaction. Rows are always touched in the same order, with the lower account id first. Money has two extra rules, which are an append-only ledger written in the same transaction and a balance that cannot be negative. The MySQL manual says that a plain `SELECT` reads a snapshot, so a check made on it does not protect a later write, and that deadlocks are normal and the transaction has to be run again. Applying ACID only to money was rejected because a repeated sign up or a double approval breaks data in the same way, and so was keeping a transaction open while the 5 second simulated AI model answers. Sources are [Isolation Levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html), [Consistent Nonlocking Reads](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/innodb-consistent-read.html), [Deadlocks](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/innodb-deadlocks-handling.html), [CHECK constraints](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html) and [commit()](https://dev.mysql.com/doc/connector-python/en/connector-python-api-mysqlconnection-commit.html). The ledger practice comes from a [payment ledger article](https://dev.to/gabrielanhaia/design-a-payment-ledger-idempotent-audit-compliant-reconciles-to-the-cent-59p7), which is guidance and not a standard. Pending, the same rules for the modules that are not built yet.

## Plain connector with a transaction helper and tenacity (2026-11-23)

The data access stays with `mysql-connector-python` and hand written SQL, with a `transaction()` helper in `db.py` and `tenacity` to repeat the operation after a deadlock. The SQL stays visible, which makes a conditional `UPDATE` easy to review, and no existing code had to be rewritten. SQLAlchemy was rejected because it would replace all the data access, its object mode hides the SQL and its main benefit, changing the database engine, is not needed. A retry decorator written by the team was rejected because a library already does it. Sources are [start_transaction()](https://dev.mysql.com/doc/connector-python/en/connector-python-api-mysqlconnection-start-transaction.html), [InternalError](https://dev.mysql.com/doc/connector-python/en/connector-python-api-errors-internalerror.html), the [deadlock page](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html), [tenacity](https://tenacity.readthedocs.io/) and [SQLAlchemy transactions](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html). The details were settled in the next decision.

## Transaction helper, retries and credit transfers (2026-11-24)

This applies the two decisions above, and the analysis is in `.sandbox/acid-analysis.md`. The connection uses autocommit, and every write goes through `transaction()` in `db.py`, which starts the transaction, commits at the end of the block and rolls back on any error. Inside it, `execute()` returns the number of changed rows and `insert()` returns the new id, and a broken unique key (error 1062) becomes `DuplicateError`. `retry_on_deadlock` runs the whole function again only for the error 1213, with 3 attempts, a random exponential wait of at most 0.5 s and `reraise=True`. The error 1205 is not repeated, because the manual says only the statement is rolled back, and `innodb_lock_wait_timeout` stays at its default. The number of attempts and the wait are a choice of the team and no source gives them.

With it, the sign up has no `SELECT` before the `INSERT`, `/api/accounts/<id>` returns only public columns to the owner or an administrator and the `PUT` changes only the name, and the error handler no longer sends the stack trace. Money uses `DECIMAL(12,2)`, because the manual calls it exact and recommends it for money, and the route validates the amount with `Decimal` first because MySQL rounds extra decimals silently even in strict mode. The tables `transfers` and `ledger_entries` were added, `accounts.balance` has a `CHECK` against negative values, and the seed gives 100.00 USD to each new account that is not an administrator through a ledger row. A transfer locks both accounts in order of id with `SELECT ... FOR UPDATE`, charges the sender with `UPDATE ... WHERE balance >= amount`, credits the recipient and writes the transfer and two ledger rows in one transaction, and the code is in `routes_credit.py`. `cursor.rowcount` counts changed rows and not matched rows, because the connection does not set `CLIENT_FOUND_ROWS`, so each conditional `UPDATE` changes a value for sure.

Tests on the real stack, after `docker compose down -v`, gave these results. Twenty sign ups with the same email created one account and 19 answers 409. Thirty transfers of 5.00 from an account with 100.00 gave 20 successes and 10 answers 402 and the balance ended at 0.00. Forty crossed transfers all worked and the total did not change. No balance was negative and each balance matched the sum of its ledger rows. A deadlock provoked on purpose was repeated and finished on the second attempt. The script is `scripts/concurrency_check.py` and it expects a fresh database. Rejected were autocommit disabled, repeating the error 1205, `SKIP LOCKED` and `SERIALIZABLE`, and integers in cents. Sources are [Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html), [Locks Set by Statements](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html), [InnoDB Error Handling](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html), [Fixed-Point Types](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html), [Rounding Behavior](https://dev.mysql.com/doc/refman/8.4/en/precision-math-rounding.html), [ROW_COUNT()](https://dev.mysql.com/doc/refman/8.4/en/information-functions.html), [cursor.rowcount](https://dev.mysql.com/doc/connector-python/en/connector-python-api-mysqlcursor-rowcount.html) and the [tenacity documentation](https://tenacity.readthedocs.io/en/latest/). Pending, whether `tenacity` is safe with threads (not stated in its documentation), the exception class of a `CHECK` violation (not tested), idempotency keys for repeated client requests, the WSTG page about usage limits (it could not be read), and the other modules, which will need a three step flow for the external call. A transfer finds the recipient by email, so it tells whether an email exists.

## Registration, approval, referrals and API keys (2026-11-24)

An account is created as `pending` and only an administrator or the robot can activate it. The role of a new account has to be one that `case.json` opens to the public, so a request with `role` set to `admin` or to an unknown role gets a 400. Before this change that request created an active administrator. The profile has two optional fields, `organization` and `country`, and the backend calls a profile complete only when both are filled and valid. The robot never decides this, because it only sends `POST /api/internal/auto-approve` and the backend applies the rule in `registration.py`. The administrator panel (`routes_admin.py` and `AdminView.vue`) lists the pending accounts with the result of that check and approves or rejects them, and a rejection needs a reason from a list kept in the backend and sends a generic email. The frontend shows what the backend sends and decides nothing, and the backend checks the role and the status again on every request.

Approval runs in one transaction. The account and its referrer are locked in order of id, the account is activated with `UPDATE ... WHERE status = 'pending'`, so a second approval changes nothing, the API key is stored and the bonus is paid. The email with the key is sent after the commit. The bonus is 5.00 USD with a limit of 5 bonuses for each referrer, and a unique key on `ledger_entries.referred_account_id` stops the database from paying twice for the same account. The count of bonuses is read after the referrer row is locked, because a plain read inside a transaction uses the snapshot of its first read and could miss a bonus committed a moment before. An account has only one valid API key, because `api_keys.account_id` is the primary key, and creating a new key replaces the old one in the same statement. The key is random (`secrets.token_urlsafe(32)`), it is sent by email and shown on screen once, and only its SHA-256 hash is stored. The libraries `email-validator` and `pycountry` are used only inside `email_address.py` and `countries.py`, so another library would replace one file each. The robot was rewritten without `system()` and `strcpy`, which closes a command injection and a buffer overflow that came from the name of the user, and the Makefile now uses the hardening flags of the OpenSSF guide. The built program is a PIE with RELRO, `BIND_NOW`, a non executable stack and the stack protector, which was checked with `readelf`. The token of the robot is compared with `hmac.compare_digest`.

Tests on the real stack gave these results. Seven approvals and one repeated approval of the same account at the same time answered seven 200 and one 409. Seven accounts referred by the same user were approved and only 5 bonuses were paid, so the balance went from 100.00 to 125.00. Every balance matched the sum of its ledger rows. The robot approved the seed account with a complete profile within one cycle and the referrer received the bonus and the email. A rejected account cannot be approved or rejected again and cannot sign in. Fifty seven unit tests pass, and a test of the lowercase rule and one of the length rule were seen failing after breaking the code on purpose. Rejected were a field that is required at registration, which would make every account complete and leave the robot with nothing to check, extra fields for each role, and a confirmation link sent by email. Mailpit accepts any recipient, so the link would show only that someone opened Mailpit. Sources read were the OWASP [Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html) and [Email Validation and Verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html) cheat sheets, which ask for a maintained library and not a custom regex, the pages of [email-validator](https://pypi.org/project/email-validator/) and [pycountry](https://pypi.org/project/pycountry/), and the [OpenSSF compiler hardening guide](https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++.html), whose last part could not be read. The CWE entries 78 and 120 were read for their titles only.

Pending, no OWASP page that was read says that a random API key can be stored with a fast hash such as SHA-256, or that it should be shown once, so both are a judgment of the team. The same OWASP sheet says that the ownership of an email must be verified before an account is enabled, and here only the approval of an administrator covers that. Anyone who writes an organization and a country gets the robot to approve the account, which is a known weakness against the referral bonus and only the limit of 5 bonuses reduces it. The default token `worker-token`, the `/api/internal` routes that nginx still forwards, the `v-html` of `LoginView.vue` and `DirectoryView.vue`, the sign up that tells whether an email exists and the limit of login attempts remain for the security block. An administrator also gets an API key if the route is called, which has no use yet. The error 1062 on a repeated referral code is not handled and the chance is very low with 64 random bits.

## Referral code collisions are left to the unique key (2026-11-24)

A referral code has 64 random bits (`secrets.token_urlsafe(8)`), so the chance that two accounts get the same code is about `n^2 / 2^65` for `n` codes, which is about 3 in 10^16 for 100 accounts and about 3 in 10^8 for a million (birthday problem, computed by hand and not taken from a source). If it happened, the unique key `uq_accounts_referral_code` would refuse the second code, the whole approval would be rolled back and the administrator would get an error 500, and approving again would create a new code. No data would be corrupted and no bonus would be paid twice. A retry with `tenacity` was rejected because the same error type also comes from the other unique keys of the approval, and a blind retry could hide a real conflict. The behaviour is written next to `_new_referral_code` in `registration.py`. An administrator can also create an API key although the account has no balance and the key has no use yet, which was accepted for the same reason, and the authentication of the agent execution will check the status of the account on every call.

## One permission policy, a robot with its own account and suspension of accounts (2026-11-24)

This replaces the parts of "Registration, approval, referrals and API keys" that say that the robot only sends `POST /api/internal/auto-approve`, that the backend alone decides the profile check and that the robot uses the shared token `WORKER_TOKEN`. It also corrects a sentence of that decision. The role and the status were not read again on each request, because `security.py` took the role from the session cookie and never looked at the status, so an administrator who was suspended kept the powers of the session for up to 30 days. Now `current_user()` reads the id, role and status from the database on each request, once per request, and a deleted account or one that is not active has no session. OWASP says that permissions have to be validated on every request, and that validating only the majority of them is not enough.

Every permission lives in `backend/app/rbac.py` as a rule of the library Cadurso, which is the only file that imports it, and the decision "Cadurso for the permission rules" at the end explains the choice. The rest of the code calls `can()` and `require()`. Each rule is a function with typed actor and resource, the roles are the main axis and a few rules add a condition on the attributes, such as the owner of an account or the profile of a registration. An account that is not active is denied before any rule runs.

The approval robot has an account with the role `bot`, created by the seed from `service_accounts` in `case.json`. Its password is a random value that nobody knows, and it cannot sign in because the policy has no `sign_in` for that role. It signs in with an API key from `WORKER_API_KEY`, which has to have at least 32 characters, and the seed stores only the SHA-256 hash and replaces it on each start, so changing the key means editing the `.env` and running the seed again with `docker compose run --rm seed`, which was tried and replaced the hash, and the robot has to be started again to read the new value. The shared token and its default value were removed. The key travels in the `Authorization: Bearer` header and a key in the URL is ignored. The robot now reads `GET /api/internal/registrations`, which returns only the id, the organization and the country, decides that a profile is complete when both are present and calls `POST /api/internal/registrations/<id>/approve` for each one. The backend applies the rule again, with the full check of the country, so the key of the robot cannot approve an incomplete profile, and an administrator can still approve any pending account. Both versions of the criterion can differ, and then the result is a 403 in the log of the robot and never an approval that should not happen. The approvals keep the id of the robot in `reviewed_by`. The policy gives the robot only the listing and the approval of registrations, and every other action gets a 403, even on its own account. The robot is left out of the directory, cannot receive credit and has no balance or referral code, and the same rule now stops credit going to administrators. The nginx of `web` answers 404 to `/api/internal/`, and the robot reaches the backend directly. The code was rewritten with `nlohmann/json`, a package of Debian that only has headers and that the team authorized, and the binary kept the PIE, RELRO, `BIND_NOW`, non executable stack and stack protector flags, checked again with `readelf`.

An administrator can suspend and reactivate any account except the own one, from the panel or with `POST /api/admin/accounts/<id>/suspend` and `/reactivate`. Each change is one transaction with `UPDATE ... WHERE status = 'active'` or `'suspended'`, so a repeated request answers 409, and it adds a row to the new table `account_status_changes` with the administrator, the old status and the new one. The columns `reviewed_by` and `reviewed_at` were not reused because they would erase who approved the account. The effect is immediate for the web session and for the API key, because both read the status on each request, and the panel shows the button that the backend sends for each account.

The results came from the real stack after `docker compose down -v`. There are 96 unit tests. Three changes made on purpose to the policy (no check of the status, a robot that ignores the profile and a robot that counts as an owner) and one to the length of the key of the seed were each detected by at least one test, and the first run of the tests found that the robot could read and rename its own account, which was corrected. A suspended administrator with an open session got a 401 and recovered the session after the reactivation. The robot approved the complete seed account within one cycle and left the incomplete one, the referrer received 5.00 USD and the email arrived. A suspended robot received a 401 in its next cycle and worked again after the reactivation. A key without a header, an invalid key and a key in the URL got 401, and a pending account that was not complete got 403 from the robot. The Playwright scripts passed with 31 of 31 checks for registration, 21 of 21 for credit and 6 of 6 for the accounts table, after the script of registration was changed to stop the robot until the step that needs it. Rejected were a column `can_sign_in`, which would be false for every robot and true for every person, so the role already says it, and a policy of our own without library, which the team did not choose. Sources read were the OWASP [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) and [REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html), and the first 39,909 of 85,397 characters of the [Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html), whose rest was received only as a summary. The Authorization sheet prefers attribute and relationship based control over RBAC alone, asks to deny by default, to centralize the failed checks and not to let a library guide the requirements. The REST sheet asks to keep keys out of the URL.

Pending, no source that was read says that the robot needs an account of its own, so it is a practice of the team. The use of the `Bearer` scheme for the key was not checked against RFC 6750. The key is found by the hash with an index of MySQL, and the comparison is not in constant time, which the team judged acceptable for a random key of 256 bits, but no source was read about it. Two administrators who suspend each other at the same moment could leave the system without an active administrator, and the account would have to be restored in the database. The session cookie still has `HttpOnly` off, the logout still accepts `GET`, and the `url` parameter of the external API, the `v-html` and the limit of login attempts remain for the security block. The robots are hidden from the directory and from the transfers, and only administrators can list the accounts, so the panel is the one place that shows the robot.

## The permission module is called rbac.py and one administrator always stays active (2026-11-24)

The module `backend/app/permissions.py` was renamed `backend/app/rbac.py`, and its tests `test_rbac.py`, because the roles are the main axis of its rules. Nothing else changed. The platform must never be left without an active administrator, since only an administrator can list the accounts, approve a registration by hand or reactivate an account. The only way to lose one in the code is to suspend it, because no route deletes an account or changes a role, and the rule that an administrator cannot suspend the own account was not enough. Two administrators that suspend each other at the same time were both authorized before either change was saved, so both ended suspended. Now every suspension runs `_keep_one_admin` inside the transaction of `change_status` in `accounts.py`. It locks the active administrators in the order of their ids with `SELECT ... FOR UPDATE` and refuses with a 409 when the account to suspend is the last of them. The second request waits for the lock, reads the result of the first and is refused, which follows the locking rules of the decision "Every write under ACID". Rejected were a database trigger, which would hide the rule outside the code that the team reviews, and a counter column, which would have to be kept equal to the real number of administrators.

A script sent 30 rounds in which two administrators suspend each other at the same moment. In every round one request worked and the other was refused with a 409 or a 401, and an administrator always stayed active, with 0 violations in two runs. With the call to `_keep_one_admin` removed on purpose, the first round left both suspended, so the check can fail. The three unit tests in `test_accounts.py` use a small double of the transaction, so they check the rule and not the lock, and one of them failed after changing the comparison to `<= 0`. The script is `.sandbox/admin_race.py`, it is not part of the delivery and it needs a second administrator created in the database. Pending, the rule only covers suspension, so a route that deletes accounts or changes roles in the future needs the same check, and the seed does not check that an administrator exists when it starts with a changed `ADMIN_EMAIL`.

## Cadurso for the permission rules (2026-11-24)

The permission rules are written with Cadurso 1.1.0 and the library is confined to `backend/app/rbac.py`. The team chose it because it has used it whenever it needed role based access control, and because it wanted a light library and not a heavy and robust authorization system such as Casbin, which was evaluated before and rejected for that weight. The assistant had recommended a small policy of its own without a dependency, because the OWASP [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) asks not to let a library guide the authorization requirements and because the project is young, and the team kept its choice. Familiarity and a small size are the reasons, and no source says that Cadurso is better than the alternatives, so that is a judgment of the team.

Before relying on it the source of the wheel 1.1.0 was read in full, which is `system.py`, `sugar.py`, `type_aliases.py`, `exceptions.py`, `errors.py` and its metadata, and it has 573 lines counting messages and docstrings. It denies by default, because the answer starts as false and only a rule that returns true changes it, and a `Veto` denies even when another rule allowed. It looks for the rules with the exact type of the actor and of the resource, so a subclass or a dictionary is denied, and a test covers that case. A rule without type annotations is stored under a class that never matches, so it is never applied and raises no error, and for that reason the rules do not use `from __future__ import annotations`. Any other exception inside a rule reaches the global handler as a 500, which also denies. The instance has to be frozen before the first query and after that it is only read. The metadata declares the MIT license.

Using it for the approval robot, the account status and the credit rules gave these results. No defect of the library appeared, and the behaviours above did not cause a failure because the tests cover the first two and the code avoids the third. The only real flaw found in the policy was a rule written by the team, where the robot counted as the owner of its own account and could read and rename it, and a unit test found it. The library itself adds little, because the lookup it performs is a few lines that search a dictionary by actor type, action and resource type. A table written by the team could have done the same in an estimated 40 to 60 lines, which was not measured. What it gives is a known structure for the rules and the `Veto`, which this project does not use. It also asks for some adjustments. Every rule takes exactly two parameters, so the actions that do not act on an account need a marker resource, which is `Platform`. The rules of one action are combined with "or", so "the owner or an administrator" are two rules. The library knows nothing about the status of an account, so `can()` denies an account that is not active before asking it.

Replacing the library would mean rewriting only `rbac.py`, because the other files call `can()` and `require()` and never import it. Not verified are the tests and the repository of the library, which were not read, and the behaviour with several threads, which its documentation does not state. From the source, after the instance is frozen it is only read, so no problem is expected with the two processes and two threads of gunicorn, but that is a reading and not a guarantee. The library has a single author and a short history, which an auditor may point out. The answer for the report is that it is confined to one file and that every rule has a unit test.

## An audit log and a MySQL user with limited privileges (2026-11-24)

The platform now keeps one table, `audit_events`, that answers who did what, when and on whom. Each row has the actor, the action with its category and its result, a timestamp in milliseconds, the account that was the target or the email that was typed when the account does not exist, and a JSON field with the old and the new values. The categories are `authn`, `authz`, `registration`, `account` and `credit`, and the action names are in snake case with a category prefix, in the style of the OWASP [Logging Vocabulary Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Vocabulary_Cheat_Sheet.html). Only `backend/app/audit.py` knows the table, and the list of actions and categories lives there. The OWASP [Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) asks for the when, where, who and what of each event, for the authentication, authorization and administration events, and for the exclusion of passwords, tokens, session identifiers and keys, so the details hold names, ids, roles, amounts, reasons and the 8 character prefix of a renewed API key, which the profile already shows, and no password, hash or whole key. A query over the table after all the flows found no secret. The address of the client and the browser are not stored on purpose, because the team chose to avoid the complications of trusting only the `X-Forwarded-For` header of nginx, and the cost is that an attack cannot be traced to an address. A failed sign in stores the typed email as it came, cut to 254 characters, and a person who writes the password in that field leaves it in the table, where only an administrator can read it.

An action that finishes writes its event in the same transaction, so both are saved or both are undone, which follows the decision "Every write under ACID". With the insert privilege removed on purpose, a credit transfer answered 500 and left the balance, the transfers and the ledger as they were. The price is that a failure of the audit table stops those actions, and OWASP does not ask for it. Refusals, failed sign ins, successful sign ins, sign outs and invalid API keys have no action to share a transaction with, so they are written in a short transaction of their own, and when that write fails the error goes only to the container log and the request goes on, as the Logging Cheat Sheet asks. With the permission removed, a sign in still answered 200. Each write also leaves a line that starts with `audit` in the container log, but the line is written before the commit and can describe an event that was rolled back, so the table is the source of truth. Only the actions that happened are recorded, so a transfer without balance or a second approval of the same account leaves no event, and the accounts created by the seed have no `user_created` event. This replaces the table `account_status_changes` and the columns `reviewed_at`, `reviewed_by` and `rejection_reason` of `accounts`, which nothing read, and it corrects the sentences of "One permission policy, a robot with its own account and suspension of accounts" that say that the approvals keep the id of the robot in `reviewed_by` and that each status change is added to that table. Who approved or rejected an account, with the reason, and who suspended or reactivated it are now events. The old entries were not edited.

The application no longer connects to MySQL as `root`. The script `database/init/99-app-user.sh` creates the user `app` with `SELECT`, `INSERT` and `UPDATE` on `accounts` and `api_keys` and only `SELECT` and `INSERT` on `transfers`, `ledger_entries` and `audit_events`, and the application has no `DELETE` anywhere because no code deletes rows. The MySQL manual says that partial revokes apply only at the schema level, so the grants are written table by table. As the user `app`, an `UPDATE` or a `DELETE` on the audit table and the ledger and a `DROP TABLE` failed with error 1142, while `SELECT ... FOR UPDATE` and `UPDATE` on `accounts` worked, and the stack ran from scratch with the new user. The Logging Cheat Sheet recommends a separate database account used only to write the log, and here the same account also writes the business tables, so the protection is that the application cannot change or erase the rows and not that a separate account writes them. In `docker-compose.yml`, `backend` and `seed` receive a list of variables and not the whole `.env`, so neither has the root password, and `config.py` reads `DB_USER` and `DB_PASSWORD` without a default value. The image of MySQL sources the `.sh` files, and an option such as `set -u` written at the top of the file broke its entrypoint, so the script runs inside a subshell. An administrator reads the log with `GET /api/admin/audit`, which has its own rule `view_audit`, filters by category, action and the email of an account, which matches the actor, the target or the typed email, and returns pages of 50 with a marker for the older ones. Each reading is recorded as `audit_viewed`, because the Logging Cheat Sheet asks to record all access to the logs. The tab Audit log only shows what the backend sends, and an email with HTML code was shown as text. There are 125 unit tests, which failed when the code was broken on purpose in five ways (no check of the action, a narrower error handler, a filter value written inside the SQL, details not decoded and a wrong category), and four browser scripts with 33, 21, 6 and 10 checks. Rejected were a container log alone, which is lost with `docker compose down` and cannot be filtered, and database triggers, which root can remove.

Pending, the Logging Vocabulary Cheat Sheet was read in full only up to its section EXCESS and the rest came as a summary, and the MySQL GRANT page was read in part through a summary. The Logging Cheat Sheet does not say how to log a failed sign in with an unknown user, so that choice is the team's. There is no hash chain or other detection of changes, no retention period and no limit on the number of events, so many refused requests fill the table until the limit of sign in attempts exists. Whoever has the root password can still change the table, since it stays in the `db` container and in the `.env`. The seed, the errors 400 and 500 and the robot cycles that find nothing to do are not recorded.
