# Architecture

This document describes how the parts of the system are connected and which part handles each task. It covers the structure that exists today and the credit transfers, so the other modules still to be built are not included. The list of services and the way to start them are in the README.

## Request flow

The browser sends every request to `web`, where nginx returns the Vue application and forwards the requests whose path begins with `/api` to the Flask backend. The backend applies the business rules, sends emails to Mailpit and calls `mock-api` whenever it needs the AI service.

```
browser -> web (nginx) -> backend (Flask) -> db (MySQL)
                                          -> mailpit (email)
                                          -> mock-api (AI service)
worker (C++) -> backend /api/internal
```

Two parts connect to the database. The backend does it for every request, and the `seed` script does it directly at startup, before the backend begins to answer. The browser also reaches Mailpit on port 8025.

## The robot

The C++ worker does not connect to the database. On a timer it asks the backend for the pending registrations, decides which ones have a complete profile and asks the backend to approve each one. The profile is complete when the organization and the country are present. The robot has an account with the role `bot` and signs in with the API key of that account, which is sent in the `Authorization` header. The key is read from `WORKER_API_KEY`, and the seed stores only its hash. The backend applies the permission policy to every call, so the robot can list the pending registrations and approve the ones with a complete profile, and every other action gets a 403. Each approval is recorded in the audit log with the robot as the actor. An administrator can suspend the account of the robot from the panel, and from then on the backend answers 401 to its key. The interval is set by `WORKER_INTERVAL_SECONDS`. The log lines carry one of the levels `DEBUG`, `INFO`, `WARN` or `ERROR`, and `LOG_LEVEL` sets the lowest one that is written, with `INFO` by default. Warnings and errors go to the error output.

## Backend

Each area of the API is a Flask blueprint registered in `backend/app/__init__.py`, and its file is named `routes_<area>.py`. The shared helpers are `config.py`, which reads the environment and `cases/marketplace/case.json`, and `db.py`, which opens one database connection for each request and provides the transactions. They also include `passwords.py`, which hashes and checks passwords and is the only file that knows the hashing library, `security.py`, which reads the signed in account from the database on each request, checks API keys, provides the `login_required` and `api_key_required` decorators and `read_json_object`, which reads the body of a request as an object, `rbac.py`, which holds the permission policy and is the only file that knows the authorization library, `mail.py` for email and `external_api.py` for the AI service. The registration module adds `registration.py`, which holds the approval, the rejection, the referral bonus and the profile check, `api_keys.py`, which creates and hashes the keys, `email_address.py` and `countries.py`, which are the only files that know the validation libraries, `accounts.py`, which lists the accounts, suspends or reactivates them and keeps at least one active administrator, `audit.py`, which writes and reads the audit log and is the only file that knows the table `audit_events`, and `routes_admin.py` for the administrator panel and the audit route. The catalog adds `agents.py`, which validates a publication, saves it as pending, approves or rejects it and lists the agents, `routes_agents.py` for the catalog routes of the signed in people and `money.py`, which turns an amount of the request into a `Decimal` and is shared by the transfers and the prices. The routes that review agents are in `routes_admin.py`, next to the ones that review registrations. The execution of agents adds `executions.py`, which holds the charge, the payment, the refund and the history, and `routes_executions.py` for its routes. The function `key_or_session_required` of `security.py` lets the same route accept an API key or a session, and a session that changes data must also send the header `X-Requested-With` and a JSON body. The routes under `/api/internal` in `routes_internal.py` are only for the robots, and nginx answers 404 to them from outside. Finally, `seed.py` creates the admin, the test accounts and two pending registrations, and prints the API key of each active account.

## Data

The table `accounts` stores the name, email, password hash, role, status and balance of each user. The status can be `pending`, `active`, `rejected` or `suspended`. At registration it is set to `pending` when the role requires approval in `case.json` and to `active` otherwise. The admin panel and the robot change it afterwards through `registration.py`, which also creates its referral code and its API key. An administrator can also move an account between `active` and `suspended`. The table `agents` holds the catalog. Its status can be `pending`, `approved` or `rejected`, a developer cannot repeat a name, the database refuses a price that is not greater than zero and only a rejected agent has a reason, which is a key of the list in `agents.py`. A review is one `UPDATE` that applies only to a pending agent, so two decisions at the same time give one answer and one 409. The test endpoint is stored and shown to the owner and the administrators, and the backend does not call it. The decision "The test endpoint of an agent is stored and never called" of `DECISIONS.md` gives the reasons. The tables `transfers` and `ledger_entries` hold the credit transfers and the append-only list of every balance change. Balances and ledger amounts have four decimals, while prices have two, so the split of a price in 80 and 20 percent is exact. The table `executions` holds each run with its idempotency key, the prompt, the answer, the cost, the two shares and its status, which is `pending`, `completed` or `failed`. An execution is charged and saved as pending in one transaction, the AI service is called outside of any transaction and the result is saved in a second one that pays the developer and the platform or refunds the user. Each of those closing steps is an `UPDATE` or a `SELECT ... FOR UPDATE` that applies only to a pending execution, so a payment and a refund cannot both happen. A pending execution that is older than two minutes is refunded when its owner reads the history or runs another agent. The account with the role `system` receives its share and a trigger of the database refuses to change its status or role. The table `audit_events` is only appended to and records who did what, when and on which account, with the old and the new values when something changed. It is written in the same transaction as the action it describes, except for refusals, sign ins, sign outs and invalid API keys, which have no action to share a transaction with and are written in a short one of their own. An administrator reads it in the tab Audit log of the panel through `GET /api/admin/audit`. The backend connects to MySQL as the user `app`, which `database/init/99-app-user.sh` creates with privileges table by table, and that user cannot update or delete rows of `audit_events`, `ledger_entries` or `transfers`. The decision "An audit log and a MySQL user with limited privileges" of `DECISIONS.md` gives the reasons. New tables go in numbered files in `database/init`, and those files run only when the database volume is created.

Every write goes through `transaction()` in `db.py`, which commits at the end of the block and rolls back on any error. A function that can meet a deadlock is wrapped with `retry_on_deadlock`. The reasons are in the decision "Transaction helper, retries and credit transfers" of `DECISIONS.md`.

## Frontend

The Vue application is in `frontend/src`. Each page is a file in `views`, and the tab Agents of the administrator panel is the component `AdminAgents.vue`, the tab Executions is `AdminExecutions.vue` and the form with the history is `ExecutionsView.vue`, the routes are defined in `router/index.js` and `api.js` wraps the calls to the backend. The signed in user is kept in the browser by `session.js`.

This description matches the code today and has to be revised whenever a module is added.
